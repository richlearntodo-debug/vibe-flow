# 言灵 Vibe Flow Remote · V2.0 产品战略（留存 · 稳定 · 零配置 · 商业化）

> 本文不是功能清单，而是**战略与留存设计**。核心问题：如何用「¥60 遥控器 + 免费输入法引擎」做出比 $15/月云端听写工具更值得留下的产品。
> 依据：仓库现状与本机实测（2026-09-09/10）、两份外部深度调研（竞品/技术，见文末）。状态：待评审。

---

## 0. 一句话战略判断

**我们不是"语音输入工具"，而是"把免费输入法引擎编排成一套可靠语音输入系统"的本地编排层。**
免费引擎决定了我们最大的成本优势（用户零使用成本），也决定了我们最大的软肋（能力上限不由我们控制）。
因此护城河只能建在三处：**① 配置成本（首次 30 秒成功）② 可靠性（每次都能落对地方）③ 编排能力（多引擎 + 多应用 + 多触发）**——这三件事恰好是竞品不会做、也做不好的（它们只支持自己的引擎）。

---

## 1. 竞争位置：用成本结构说话

| 方案 | 用户成本 | 引擎 | 使用量限制 | 隐私 |
|---|---|---|---|---|
| Wispr Flow | $15/月（$12 年付） | 自有云 LLM | 免费档 2000 字/周 | trial/standard **默认**拿音频+转写训模型 |
| Typeless | $30/月（$144/年） | 自有云模型 | 免费档 8000 词/周 | 营销称 on-device，实际音频在云端 |
| superwhisper | $84.99/年 或 $249 买断 | 本地/自有 | 免费档有限 | 本地模型可离线 |
| **言灵 Vibe Flow** | **¥60 遥控器（一次买断）** | **微信/豆包/讯飞/Win+H 等自带免费引擎** | **取决于所选输入法（多数无限制）** | **不读/不存/不上传（架构事实）** |

**结论**：我们的对手不是"另一个输入法"，而是"用户觉得没必要装另一个软件"。所以产品的第一目标不是功能多，而是**让它值得被装第二次（留存）**。

**成本优势的前提是体验必须达标**：用户为省 $15/月 而接受"偶尔不出字、装驱动重启、每题都要配"，是不可持续的。**稳定性与配置成本是商业模式的生死线**，不是体验加分项。

## 2. 本次实测得出的三个决定性发现

### 发现 1：CABLE Output 是「线路」形态，部分输入法根本看不见它

| 录音设备 | Windows 端点形态（`PKEY_AudioEndpoint_FormFactor`） |
|---|---|
| **CABLE Output（我们的虚拟麦克风）** | **2 = LineLevel（线路输入）** |
| Realtek 麦克风 | 4 = Microphone |
| HUAWEI 耳机 | 5 = Headset |

- 豆包输入法的麦克风列表**找不到 CABLE Output**，实测其音频端点确实是线路形态 → 高度符合"输入法按形态过滤，只列麦克风/耳机"。
- VB-CABLE 的 INF **没有声明 FormFactor**（只声明了 Association 与 ControlPanelProvider）→ 该值来自端点属性存储的默认值。
- 注册表直改**不可行**：`MMDevices\Audio\Capture\{guid}\Properties` 的 ACL 只给 `Audiosrv`/`AudioEndpointBuilder`/`SYSTEM`/`TrustedInstaller`，管理员进程写入被拒。
- **✅ 已验证（PoC-1 实跑成功，2026-09-10）**：`IMMDevice::OpenPropertyStore(STGM_READWRITE) + SetValue(PKEY_AudioEndpoint_FormFactor=4) + Commit()` **三个 HRESULT 全 0x0，普通中等权限进程即可，免管理员、免改 ACL、免重启音频服务**；注册表值由 2 持久变为 4，新实例读回即 4。已实测还原（设回 2）同样成功。
  → **产品含义**：把所有"只列麦克风"的输入法（豆包等）拉进隔离音质模式的钥匙握在我们手里，而且竞品未发现此路。**注意是未文档化行为**（微软措辞为 "should not set"），必须：① 可逆、提供一键还原；② 驱动重装/端点 GUID 重建后自动重放；③ 写进兼容性风险与免责说明。

### 发现 2：免驱动模式在架构上已具备（= 零配置首次成功）

配置项 `autoRouteVirtualMicrophone`（界面文案「听写时自动使用遥控器麦克风（推荐）」）控制"听写时是否把默认录音设备切到 CABLE Output"。
**关掉它** = 遥控器只当**无线触发器**（按键去触发输入法语音），音频由**电脑/耳机麦克风**采集。于是：

- **不需要 VB-CABLE、不需要管理员、不需要重启** → 安装到能用约 30 秒；
- 对「只听自己麦克风的输入法」（豆包）**天然可用**（它本来就用真实麦克风）；
- 代价：音质取决于电脑麦克风、会采集环境声（隐私需明确披露）。

**产品含义**：把免驱动模式做成**首次体验与驱动失败兜底**（保证 5 分钟内拿到第一段文字），把隔离模式做成**日常推荐与"音质/隐私增强包"**。这一条同时解决了「配置成本高」和「首次成功率」两个留存死穴。
**定位修正（采纳留存调研结论）**：免驱动模式**不宜做成长期默认**——音质下降（远场混响 + 环境噪声）且采集范围扩大到整个房间，隐私姿态变弱。正确姿势：**首启默认跑免驱动拿到首次成功 → 首次成功后引导切到隔离模式（推荐）→ 设置页随时可切、可解释差异**。

### 发现 3：注入过滤是系统级安全契约，不可绕过；但仍有非注入路径

- `KBDLLHOOKSTRUCT.flags` 的 `LLKHF_INJECTED` 是公开契约，输入法挂低级钩子即可整体丢弃注入（豆包实测：`keybd_event`、`SendInput` 扫描码、模拟鼠标点击全部无效，真人按键有效）。**不要在产品里承诺"绕过"。**
- **🔑 新发现（本轮二进制取证，最有希望的一条）**：豆包自己同时实现了**两条机制**——`InstallVoiceKeyHook`/`VoiceKeyHookProc`（低级键盘钩子，会丢弃注入）**和** `RegisterHotKey`/`ProbeGlobalHotKey`/`shortcut_validator.cpp`（系统全局热键）。而**系统热键匹配发生在系统输入处理路径，与钩子过滤是两套机制**，普通 `SendInput` 注入很可能能触发 `WM_HOTKEY`。
  → **PoC 1-A（最高优先，1–2 小时）**：把豆包配置 `voice.enableGlobalVoiceShortcut` 改为 `true`（本机默认 false），再注入其全局语音组合键，看语音面板是否被唤起。**若成立，"豆包远程唤醒"直接解锁，且这是完全合规的公开机制（用户自己软件的公开设置项）。**
- 其余替代路径（按优先级）：**② UIA 写值**（`ValuePattern.SetValue`）投递文字，不产生键盘事件；**③ 剪贴板 + 受控 Ctrl+V**（现状，仅对不拦注入的引擎有效）；**④ MSAA `accDoDefaultAction`**（豆包悬浮条是 DirectUI；但 UIA 树为空很可能意味着它连 MSAA 也没实现，概率偏低，值得一次性判死）；**⑤ 免驱动模式**（唯一 100% 确定的豆包可用路径）。

## 3. 留存模型：五阶段漏斗与对应机制

> 留存的本质：**让用户在 10 分钟内成功一次、在 3 天内形成习惯、在 30 天内积累到"离开就会损失"的个人化资产。**

### 阶段 1 · 激活（下载 → 首次成功）
| 机制 | 说明 |
|---|---|
| **零配置首次成功**（P0） | 默认免驱动模式：装完即用，遥控器按键 → 电脑麦克风 → 输入法 → 文字入框；全程无驱动、无重启、无管理员 |
| **向导强制走通一次真机听写** | 复用现有五项任务向导的真机门禁：没真正出过一次字，不许"完成"（这是激活率的关键） |
| **失败即给一键修复** | 每个失败界面必须带一个"点这里就能修"的动作，禁止只报错误码 |
| **3 分钟上限** | 从安装到首次成功的目标时长；超出即视为引导设计缺陷 |

### 阶段 2 · 习惯（第 1–7 天）
| 机制 | 说明 |
|---|---|
| **一个动作闭环** | 按住说 → 松开 → 文字落进当前输入框；不切窗口、不点鼠标、不看屏幕 |
| **触感与听觉反馈** | 遥控器按键的物理反馈 + 录音/完成提示音（现有 `soundFeedbackEnabled` 细分）→ 形成肌肉记忆，不必看 HUD |
| **每天都用得上的场景** | 聊天/邮件/写作、IDE 与终端、会议与演示、离键盘场景（沙发、站立、动感单车）——在首页把"今天可以这样用"讲清楚 |
| **常驻但不打扰** | 托盘 + 悬浮窗；不抢焦点；开机自启（现有能力） |

### 阶段 3 · 信任（第 1–30 天，决定是否流失）
| 机制 | 说明 |
|---|---|
| **投递回执** | 每次会话后明确显示"已投递到 <应用>（引擎/策略/耗时）"或"未投递 + 原因 + 一键重试" |
| **自愈与体检** | 会话前 2 秒体检；断流/断连/路由丢失自动恢复；提供"一键修复全部" |
| **稳定性指标可见** | 断连次数、断流时长、失败率、最近错误——把可靠性变成可看见的东西 |
| **永不静默失败** | 宁可弹提示，也不无声无息地丢字（这是当前最大的信任杀手） |

### 阶段 4 · 渐进（个人化资产 = 迁移成本）
| 机制 | 说明 |
|---|---|
| **按应用工作流卡片** | 每个应用记住：语音工具 + 按键层 + 投递策略 + 风格提示；用一次就更准一点 |
| **术语包** | 用户录入的术语/专有名词，可导出给各输入法（不涉及转写文字） |
| **常用片段** | 遥控器按键触发的用户自建文本（走 UIA 写值，不走剪贴板） |
| **自动学习输入目标** | 第一次在某个应用里成功输入后，询问"记住这个应用吗？"——把配置成本转成一次性确认 |
| **元数据统计** | 累计字数/节省时长/连续天数/按应用分布（不保存文字）→ 成就感 + 习惯循环 |

### 阶段 5 · 身份与传播（30 天+）
| 机制 | 说明 |
|---|---|
| **配置分享/导入** | 工作流卡片、术语包、按键层导出为 JSON → 社区分享（开源项目的天然增长回路） |
| **预设市场（轻量）** | 官方维护一批"场景预设"（VSCode 编程、客服回复、会议记录…）一键导入 |
| **可审计的隐私叙事** | "白皮书 + 日志字段清单"，把隐私优势变成可验证的品牌资产 |
| **贡献路径** | 引擎适配器（新增输入法支持）以插件/配置文件形式开放，社区可贡献 |

**本产品独有的留存资产**（竞品难以复制）：① 遥控器的物理触感与肌肉记忆；② "离键/手占用"场景（演示、站立、动感单车、无障碍）；③ 免费引擎带来的零使用成本；④ 多引擎编排能力（用户不必在"用哪个输入法"上做取舍）。

## 4. 稳定性工程（用户第一痛点）

**目标口径：连续 7 天、每天 30 次听写，不出一次"无声失败"。**

| 层次 | 措施 |
|---|---|
| **会话前** | 2 秒体检门禁：遥控器在线？桥接健康？引擎进程在？快捷键一致？录音设备正确？投递目标存在？→ 任一不合格就**不开始**，直接给原因 + 一键修复（禁止"开始了但没反应"） |
| **会话中** | 音频断流检测（帧间隔/丢包/最大间隙超阈值即 HUD 告警）；录音中遥控器掉线自动重连；按键卡死看门狗（已有） |
| **会话后** | 投递校验与回执；失败自动降级（UIA 写值 → 受控回填 → 提示手动）；一键重试 |
| **组件层** | Bridge/Capture 看门狗与自动重启；Explorer 重启后托盘自愈；蓝牙/睡眠唤醒后的恢复序列（端点重枚举 → 重连 BLE → 重注册托盘 → 复核热键） |
| **诊断层** | 连接质量面板：断连次数、断流总时长、重连耗时、最近错误、电量（待 PoC）；一键导出脱敏诊断包 |

**电量与断流的关系值得优先验证**：本机曾出现 0.5–1.1 秒音频断流（`max_gap_ms` 553/1109）——若与遥控器低电量相关，则"电量预警"就是最直接的稳定性功能（BLE 连接态拿不到 RSSI，但电量可尝试 WinRT Battery / GATT `0x180F`）。

## 5. 零配置成功率：三条安装路径

| 路径 | 前置条件 | 体验 | 适用人群 |
|---|---|---|---|
| **A. 零配置模式（默认）** | 无需驱动/管理员/重启 | 装完 30 秒可用；遥控器当触发器，电脑麦克风采集 | 所有新用户、笔记本、公司锁权限机器、驱动装不上的人 |
| **B. 隔离模式（推荐升级）** | 内置 VB-CABLE 一键安装（+重启续做） | 遥控器麦克风 → CABLE → 引擎；音质与隐私最好 | 追求音质/嘈杂环境/隐私敏感用户 |
| **C. 复用已有虚拟声卡** | 用户已装 VB-CABLE/Voicemeeter/VAC | 自动探测并适配，不重复安装 | 进阶用户、已有直播/录音环境 |

**实现要点**
1. **内置驱动**：安装包已带官方 Pack45（许可允许随产品分发、可静默安装；A+B/C+D 不可捆绑）；安装器补齐"检测 → 静默安装 → 重启提示 → **重启后自动续做**（复用现有 `resumeSetupAfterRestart`）→ 装完自检"。
2. **驱动态探测与修复**：端点存在但被禁用、采样率不匹配、独占模式、"侦听此设备"造成回声、默认设备被改——每项都要有检测与一键修复。
3. **模式可切换、可回退**：任何时刻可在"语音"页切换 A/B/C，切换不失效已有配置，失败自动回退到 A。
4. **诚实披露**：A 模式会采集环境声（输入法用它自己的麦克风），必须在首次选择时说清楚；B 模式只采遥控器麦克风。

## 6. 引擎适配框架（"支持更多输入法"，含豆包）

现状问题：每个引擎的上屏方式都不同（直写 / 剪贴板 / 需要激活 / 过滤注入），硬编码三家不可持续。

**适配器契约（每个引擎一份声明式配置 + 少量代码）**
```
激活：热键注入 | 工具栏 UIA 点击 | 状态栏 MSAA 调用 | 仅手动
停止：再次激活 | 自动（松开后引擎自行结束）
投递：引擎直写 | 剪贴板+受控粘贴 | UIA 写值
校验：目标焦点 / 剪贴板序列号 / 文本长度指纹（可选，需显式开启）
能力：是否需要激活输入法 / 是否需要驱动 / 是否过滤注入 / 冷启动耗时
```

**豆包的支持路径（按可行性排序）**
1. **PoC-2：MSAA 调起**（`AccessibleObjectFromWindow` + `accDoDefaultAction` 点它的麦克风按钮）→ 若成功，豆包可自动化激活。
2. **PoC-1：端点形态改写** → 若 CABLE Output 能被列进豆包麦克风列表，隔离模式即可直供音频。
3. **兜底：零配置模式 + 手动开面板**（豆包用自己的麦克风，用户按一次快捷键即可；言灵负责其余一切）。
4. **诚实提示：换引擎更省事**（在"语音"页给出该应用的推荐引擎）。

**目标：把"支持更多输入法"变成"声明式新增一个适配器"，而不是每次改核心代码。**

## 7. 遥控器价值最大化（"更多快捷键" = 层 + 手势 + 宏）

13 个物理键不该只有 13 个动作：

| 能力 | 说明 |
|---|---|
| **手势** | 单击 / 双击 / 长按（现有配置格式已支持 `:short`/`:long`，补齐双击与冲突消解） |
| **层（Layer）** | 长按某键进入第二层，层内其余按键执行备用动作（例：长按 Home 进入"语音层"：方向键=切引擎/重试投递/取消听写/切换输入目标）——13 键可扩展到 30+ 动作 |
| **组合** | 两键组合（如 Home+方向） |
| **宏** | 动作序列（按键、延时、打开应用、发送快捷键），V1.5 起一直 deferred，本次应补上 |
| **语音动作** | 专属动作集：切引擎、重试投递、取消本次、显示/隐藏 HUD、切换输入目标、暂停/恢复桥接（双击语音键） |
| **按应用不同层** | 复用 Smart Profiles：在 IDE 里是"代码层"，在聊天里是"回复层" |

## 8. 自动化识别（把配置成本转成自动行为）

| 自动化 | 做法 | 收益 |
|---|---|---|
| **活跃输入法检测** | 查询前台线程当前输入法（TSF `ITfInputProcessorProfileMgr::GetActiveProfile`，回退 IMM32）→ 自动选择投递策略 | 用户不必理解"为什么这个应用要手动粘贴" |
| **输入目标自动学习** | 首次成功投递后询问"记住此应用？"（一次确认代替手动学习+测试） | 直接砍掉最大的一块配置成本 |
| **按应用路由** | 工作流卡片：应用 → 引擎 + 层 + 策略 + 风格提示 | 用一次更准一次，形成依赖 |
| **录音前自动体检** | 见第 4 节 | 把"偶发失败"变成"提前拦下" |
| **主动修复建议** | 检测到某引擎在该应用不可用（如过滤注入）→ 推荐可用引擎并一键切换 | 把"我们做不到"变成"我们替你选好了" |

**定位口号候选**

**三个必答质疑**
| 质疑 | 回应框架 |
|---|---|
| 录音会上云吗？ | 录音只在本机虚拟声卡与输入法之间流动；言灵不读、不存、不上传；给出日志字段清单与白皮书 |

| 为什么要买遥控器？ | 因为它把"三次点击 + 找焦点"变成"一个动作"；而且 ¥60 一次买断，对比 $15/月 的云端工具，一个月就回本 |

### 16.5 稳定性诊断（BLE 遥控器）

- 连接态**拿不到 RSSI**（公共 API 只在广播/发现阶段提供）——不要在 UI 承诺"信号强度"。
- 可用代理指标：**GATT 读往返耗时**（定期读 `0x2A19`/`0x2A24` 计时）、**ATVV 帧间隔 P50/P95/P99 抖动**、断连/重连计数、**电量**（标准 Battery Service `0x180F`/`0x2A19`）。
- 「低电量导致音频断续」**没有权威产品级结论**（仅专利级论述）；本机观察到的 0.5–1.1 秒整段断流更像连接事件丢失/宿主抢占/驱动重启，**必须做"同位置满电 vs 低电各 30 次"的相关性实验**才能归因。
- **上线门槛**：能提前 ≥300ms 预警且误报 <10% 才做 UI 预警，否则只做事后诊断（避免"狼来了"消耗信任）。
